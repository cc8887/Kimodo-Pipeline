# 从零安装 Kimodo，再用当前 Pipeline 生产和检查动作

核查日期：2026-10-11。本教程以 **Windows + WSL2 Ubuntu + NVIDIA 显卡** 为主要方案，同时提供当前本机的 Windows 快速入口和 CPU 方案地址。

你会用到两个工具：NVIDIA Kimodo 负责生成源动作；此仓库负责 ALS 制作规则、重定向、Root/Pelvis、曲线、FBX 回读、Godot 验证与 Motion Viewer。Kimodo 自带的 `kimodo_demo` 与本仓库的 Motion Viewer 是两个网页。

## 0. 先认清三个目录和两个终端

| 名称 | 位置约定 | 用途 |
|---|---|---|
| 独立生产工具 | 自行选择的 Windows 目录；下文从这个仓库根目录开始 | 本仓库，使用 Git 管理 |
| Kimodo 后端 | WSL `~/Github/kimodo` | 模型、依赖和生成环境；大模型缓存放 Linux 文件系统 |
| Godot 消费项目 | 建议与工具目录同级，配置中使用 `../Godot-Locomotion` | 导入与实际游戏验证 |

标注 **PowerShell** 的命令在 Windows 终端执行；标注 **WSL Bash** 的命令在 Ubuntu 终端执行。Windows 文件在 WSL 中使用 `/mnt/<盘符>/...` 的形式，具体路径由工具转换；虚拟环境、Python 和模型缓存不能直接跨系统混用。

先取得本仓库源码。在文件管理器打开仓库文件夹，右键选择“在终端中打开”，使用 PowerShell，确认能看到 `README.md`，记录当前目录：

```powershell
$PipelineRoot = (Get-Location).Path
Test-Path README.md
```

应输出 `True`。下文 Windows 命令中的 `$PipelineRoot` 就是这个目录；另开终端时先在仓库根目录重复这两行。工具仓库和 Godot 项目放在 Windows 共享文件系统，Kimodo 后端与模型放在 WSL 的 Linux 文件系统。

当前电脑已有可用 Windows Kimodo 后端，实际位置由被 Git 忽略的 `pipeline.local.toml` 记录。想立即使用现有环境，直接看第 5 节；想重新搭建 WSL，从第 1 节开始。新工具无需安装 UE 或 Blender。

## 1. 安装 WSL2 和检查显卡

在开始菜单搜索 PowerShell，选择“以管理员身份运行”。第一次安装执行：

```powershell
wsl --install -d Ubuntu-24.04
```

按提示重启，打开 Ubuntu，创建 Linux 用户名与密码。输入 Linux 密码时没有星号属于正常现象。如果已装 Ubuntu，先执行下面两个检查即可，不需要重复安装发行版：

```powershell
wsl --update
wsl --list --verbose
```

你的 Ubuntu 行应显示 `VERSION 2`；确实为 1 时用其实际名称执行 `wsl --set-version Ubuntu 2`。参考 [微软 WSL 安装文档](https://learn.microsoft.com/en-us/windows/wsl/install)。

安装或更新 **Windows NVIDIA 显卡驱动**，然后在 WSL Bash 执行：

```bash
nvidia-smi
```

应能看到自己的显卡。命令不存在时可试 `/usr/lib/wsl/lib/nvidia-smi`。WSL 的 GPU 驱动由 Windows 提供，不要照普通 Linux 教程在 WSL 内另装 `nvidia-driver`。参考 [微软 WSL GPU 文档](https://learn.microsoft.com/en-us/windows/wsl/tutorials/gpu-compute)。

在 WSL Bash 安装构建工具：

```bash
sudo apt update
sudo apt install -y git python3 python3-venv python3-pip build-essential cmake ninja-build
python3 --version
```

Ubuntu 24.04 的 Python 3.12 适合此教程；本生产工具要求 Python 3.11+。模型下载、CPU 文本编码和生成需要较大的磁盘/内存余量。具体硬件表现以自己的实际运行结果为准。

## 2. 申请 Llama 模型权限

1. 注册并登录 [Hugging Face](https://huggingface.co/join)，完成邮箱验证。
2. 使用同一账号打开 [Meta-Llama-3-8B-Instruct 模型页](https://huggingface.co/meta-llama/Meta-Llama-3-8B-Instruct)。
3. 页面要求填写信息或接受条款时，按页面提交访问申请。等页面确认可以访问该模型；申请已提交不等于下载权限已经通过，审批时间以平台为准。
4. 获得权限后，到 [Hugging Face Token 设置](https://huggingface.co/settings/tokens) 创建具有读取该模型权限的 token。
5. 下一节在自己的终端运行 `hf auth login`，按提示输入 token。不要把 token 写进 Git、local TOML、命令历史示例或聊天。

**仓库可以下载，不代表 Llama 权限已开通。** 模型下载遇到 401/403 或 `GatedRepoError`，先核对授权账号与终端登录账号一致。官方入口见 [Kimodo 安装说明](https://github.com/nv-tlabs/kimodo/blob/main/docs/source/getting_started/installation.md)。

## 3. 下载和安装 Kimodo：WSL 方案

在第 0 节的 **PowerShell** 中，进入共享工具目录对应的 WSL 终端：

```powershell
wsl -d Ubuntu --cd $PipelineRoot
```

`Ubuntu` 要换成 `wsl --list --verbose` 中实际的发行版名称，例如第 1 节新装的 `Ubuntu-24.04`。以下在打开的 **WSL Bash** 执行，先记录工具根目录，再下载后端：

```bash
export KIMODO_PIPELINE_ROOT="$PWD"
test -f "$KIMODO_PIPELINE_ROOT/README.md" && echo "Pipeline directory found"
mkdir -p ~/Github
cd ~/Github
git clone https://github.com/nv-tlabs/kimodo.git
cd kimodo
python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip setuptools wheel
```

最开始应看到 `Pipeline directory found`；没有这行时，先退出 WSL，按第 0 节在正确的仓库目录重新进入。如果 `~/Github/kimodo` 已存在，进入现有目录查看 `git status`，不要直接覆盖它。官方源仓库：[nv-tlabs/kimodo](https://github.com/nv-tlabs/kimodo)。

先安装与你的显卡、驱动匹配的 PyTorch。到 [PyTorch 官方选择器](https://pytorch.org/get-started/locally/) 选择 Linux / Pip / Python / CUDA，并复制其命令。下面是 CUDA 12.8 路线的示例，不代表所有电脑都应选择同一版本：

```bash
python -m pip install torch --index-url https://download.pytorch.org/whl/cu128
python -c "import torch; print(torch.__version__); print(torch.cuda.is_available()); print(torch.cuda.get_device_name(0) if torch.cuda.is_available() else 'CUDA unavailable')"
```

GPU 路线应看到 `True` 和自己的显卡。RTX 50 系列还应确认 PyTorch 构建支持显卡架构；遇到 `no kernel image`，重新核对官方安装选择器，不能只凭 `nvidia-smi` 判断 PyTorch 已可用。

安装官方 Kimodo 和可选网页依赖：

```bash
python -m pip install -e ".[all]"
python -m pip install --upgrade huggingface_hub
hf auth login
hf auth whoami
```

本教程走源码安装，MotionCorrection 的 C++ 扩展需要前面安装的构建工具。安装方法来自 [官方虚拟环境安装文档](https://github.com/nv-tlabs/kimodo/blob/main/docs/source/getting_started/installation_virtual_env.md)。

### 3.1 先下载模型：此 Pipeline 的批量模式会使用离线缓存

本 Pipeline 默认规则使用 `Kimodo-SOMA-RP-v1.1`。作者批量模式启用本地离线缓存，所以第一次不能指望生产命令自动联网补齐权重。

在激活 Kimodo 环境的 WSL Bash 中执行：

```bash
cd ~/Github/kimodo
export HF_HUB_CACHE="$PWD/.cache/huggingface/hub"
mkdir -p "$HF_HUB_CACHE"
hf download meta-llama/Meta-Llama-3-8B-Instruct
hf download McGill-NLP/LLM2Vec-Meta-Llama-3-8B-Instruct-mntp
hf download McGill-NLP/LLM2Vec-Meta-Llama-3-8B-Instruct-mntp-supervised
hf download nvidia/Kimodo-SOMA-RP-v1.1
```

这些命令下载完整对应仓库，不要只保留配置文件。使用 [Hugging Face CLI](https://huggingface.co/docs/huggingface_hub/guides/cli) 登录和下载；首次下载时间主要取决于网络与模型大小。遇到网络错误应完成下载后再生产，不要修改门禁绕过缓存缺失。

新 WSL 环境用标准 HF 缓存即可。当前 Windows 后端另外支持本地 Llama base 路径；相关本机改动已保存到 `patches/kimodo-local-llama.patch`，仅在需要复现这项路径覆盖时使用。对匹配版本先运行 `git apply --check`，不要把它当作所有上游版本都适用的安装步骤。

### 3.2 先用官方命令生成一个短动作

```bash
export TEXT_ENCODER_DEVICE=cpu
kimodo_gen "A person walks forward at a steady pace." \
  --model Kimodo-SOMA-RP-v1.1 \
  --duration 2.0 \
  --bvh --bvh_standard_tpose \
  --output ./output/first_walk
```

`TEXT_ENCODER_DEVICE=cpu` 把 Llama 文本编码放到 CPU，动作扩散模型仍可运行在 GPU。官方 [Quick Start](https://github.com/nv-tlabs/kimodo/blob/main/docs/source/getting_started/quick_start.md) 推荐显存不足时用此方式。首次编码会加载较大的文本模型，短时间没有新日志不一定是卡死。

这一步只证明官方 Kimodo 能生成源动作，尚未进入 ALS 重定向或游戏验收。需要官方编辑网页时可运行 `kimodo_demo`，按终端打印的地址打开；它不是下面的 Motion Viewer。

## 4. 安装独立 Pipeline，连接 Godot 项目

生产工具位于第 0 节选择的目录，当前有独立本地 Git 仓库；尚未配置远程。另一台电脑需取得此仓库源码，并单独准备原版 ALS 导出与消费项目。模型、reference 快照和生成资产不会跟随 Git 下载。

### 4.1 Windows 侧准备运行验证 Python

Godot 消费项目和它的 Godot/.NET 是 Windows 环境，因此用一个小型 Windows Python 环境处理导入与游戏验证。**PowerShell**：

首次使用这台电脑时，先安装 [Windows Python](https://www.python.org/downloads/windows/) 的 3.12 x64 环境并确认 `py -3.12 --version` 可执行。消费项目当前使用 `Godot.NET.Sdk/4.7.2`、`net8.0`；从 [Godot 官方 Windows 下载入口](https://godotengine.org/download/windows/) 取得匹配的 **.NET 版**，安装 [.NET 8 SDK](https://dotnet.microsoft.com/en-us/download/dotnet/8.0)。SDK 下载项与仅用于运行程序的 Runtime 下载项用途不同。把这些实际可执行文件路径填入下一节配置；已有可用环境可跳过安装。

```powershell
cd $PipelineRoot
py -3.12 -m venv .venv-win
& .venv-win\Scripts\python.exe -m pip install --upgrade pip
& .venv-win\Scripts\python.exe -m pip install -e .
```

本电脑该环境已经建立，不必重复创建。安装会提供 NumPy、SciPy 和固定 `ufbx==0.0.5`；不需要在这个小环境里再安装 Llama 或 Torch。

### 4.2 在 WSL 的 Kimodo 环境安装 Pipeline

**WSL Bash**：

```bash
source ~/Github/kimodo/.venv/bin/activate
cd "$KIMODO_PIPELINE_ROOT"
python -m pip install -e .
cp config/pipeline.wsl.example.toml pipeline.wsl.local.toml
```

用编辑器打开 `pipeline.wsl.local.toml`，把以下字段改成自己的真实位置：

| 字段 | 作用 |
|---|---|
| `kimodo_repo` / `python` | WSL 中 Kimodo 源码与 Linux Python |
| `project_root` | Godot 消费项目；同级目录可保留 `../Godot-Locomotion` |
| `runtime_python` | Windows 验证 Python；保留 `.venv-win/Scripts/python.exe` |
| `godot` | 实际 Windows Godot .NET 版的位置；模板使用消费项目中的相对路径 |
| `dotnet` | Windows SDK 可执行文件；模板从 `KIMODO_DOTNET` 环境变量读取 |
| `asset_root` / `reference_root` | 独立工具自己的参考/生产目录，初次保留 `workspace/als` |
| `work_root` | 每个批次的日志目录，初次保留 `workspace/runs` |

所有相对路径都以工具仓库根目录为基准，`~/` 表示当前系统用户目录。目录布局不同时，只修改自己的 local 配置；这些文件已被 Git 忽略。

每次 WSL 工作先回到工具根目录、选择配置，并取得 Windows dotnet 的路径：

```bash
cd "$KIMODO_PIPELINE_ROOT"
export KIMODO_PIPELINE_CONFIG="$PWD/pipeline.wsl.local.toml"
export KIMODO_DOTNET="$(wslpath -u "$(powershell.exe -NoProfile -Command '(Get-Command dotnet.exe -ErrorAction Stop).Source' | tr -d '\r')")"
test -f "$KIMODO_DOTNET" && echo "Windows dotnet found"
```

应看到 `Windows dotnet found`。若 Windows 终端找不到 `dotnet.exe`，先完成 .NET SDK 安装并重新打开终端。也可把确认过的可执行文件路径直接写入自己的 local TOML。另开 WSL 终端时，先按第 3 节从 PowerShell 进入工具目录并设置 `KIMODO_PIPELINE_ROOT`，再执行上面这一组命令。

### 4.3 准备不可变原版参考快照

Godot 项目必须已有原版 `assets/config` 和 `assets/generated/als_v4` 导出；只克隆项目代码不够。第一次在 **WSL Bash** 执行：

```bash
python -m tools.reference_snapshot
python -m tools.doctor --verify-reference
```

本电脑已有 `workspace/als/reference.json`，直接运行第二条检查即可；导出器拒绝覆盖已有快照。需要更新参考时，指定新的 `--output`，同步修改两个 local 配置中的参考与资产根目录，不在旧快照上改字节。

检查结果应有 `"passed": true`。这个检查核对文件、路径和依赖，不会替你申请模型权限，也不代表已完成真实生成或 GPU 验证。

## 5. 如何使用当前 Pipeline

### 5.1 先看计划

**WSL Bash**，保持 Kimodo 环境激活且已选择 WSL local 配置：

```bash
python tools/produce_als_resources.py inspect --scope run
python tools/produce_als_resources.py plan --scope run --output workspace/plans/run_first
```

`plan` 生成 `graph.json` 与 `graph.mmd`，不会生成动作。依赖图包含完整资产目录，当前 scope 的目标及其依赖闭包决定实际执行范围，不能用图的总节点数当作本次生成数量。

| scope | 当前用途 |
|---|---|
| `non-prop` | 完整非道具生产范围 |
| `run` | 跑步六方向、V4/Refactored 十二个身份 |
| `crouch` | 蹲走前后及纯左右 |
| `air` | Fall / Fall_Fast / Flail / Air Lean |
| `mantle` | 低、中、高攀爬制作与相关验收 |
| `derived` | 用显式上游回执补可派生身份 |

### 5.2 生产一个新批次

先用较小的 `run` 或 `crouch` 范围熟悉流程。**WSL Bash**：

```bash
export TEXT_ENCODER_DEVICE=cpu
python tools/produce_als_resources.py run --scope run --keep-going
```

完整非道具范围使用：

```bash
python tools/produce_als_resources.py run --scope non-prop --keep-going
```

默认完整执行：生成/母动作/派生 → 纯脚本目标重定向 → 有界修复与 Root/Pelvis → 曲线 → 最终 FBX 回读 → 复制到 Godot 新版本目录 → Optimize 构建、Godot 导入、六域绑定与相关场景验证。WSL 调度到 Windows 的路径转换由运行适配器完成。

每批自动使用独立的工作目录和版本名。终端结束后查看 `workspace/runs/<本次批次>/` 下作者报告及 `full-pipeline/result.json`；制作包在 `workspace/als/assets/generated/als_nonprop_<版本>/`。失败也会保留已完成独立分支和明确缺失，不要删除失败日志或反复覆盖同名版本。

小范围通常不足以满足完整非道具闭包，会形成诊断包。`pipeline_complete_rejected`、`productionReady=false` 或非零退出码需要结合具体门禁报告阅读；文件存在或 Viewer 能播放不代表可正式启用。

### 5.3 在已有包基础上补做

使用 `--base-pack` 保留已有交付来源。例如：

```bash
python tools/produce_als_resources.py run --scope run --keep-going \
  --base-pack workspace/als/assets/generated/YOUR_WSL_PRODUCTION_VERSION/resource-pack.json
```

把占位名称换成自己此前在 WSL 生产的版本。选择**制作原包**作为基线，保留作者回执和源文件；Godot 部署副本会适配路径和绑定，其用途是消费与验证。只有来源回执和所有哈希有效的旧包才能保留，不能只拷贝同名 FBX。

当前 Godot 项目的历史包由 Windows 作者环境制作，上游回执包含 Windows 绝对路径。这些历史包在本机 Windows 后端下可以用 `--base-pack` 续作，但不能把外层路径改成 `/mnt/...` 就交给 WSL 复用。第一次 WSL 生产不加该选项；之后再复用 WSL 自己的制作原包。要定位 Windows 活动包，查看消费项目 `assets/config/als_resource_pack.json` 的 `pack` 字段，去掉 `res://` 后拼到项目目录。

`--upstream-receipts` 是另一种显式复用作者节点的方式，适用于已知道上游批次的诊断/补做；原作者回执必须仍能访问其源文件。跨电脑搬运旧作者历史尚不能只复制一个 JSON。

### 5.4 本电脑的 Windows 快速入口

无需 WSL，直接在 **PowerShell**：

```powershell
cd $PipelineRoot
& .venv-win\Scripts\python.exe -m tools.doctor --verify-reference
$env:TEXT_ENCODER_DEVICE='cpu'
$KimodoPython = (& .venv-win\Scripts\python.exe -c "from tools.kimodo_pipeline.paths import configured_path; print(configured_path('python'))")
& $KimodoPython tools\produce_als_resources.py run --scope run --keep-going
```

根目录已有 `pipeline.local.toml`，连接当前 Windows 后端和消费者。不要用 `.venv-win` 来做模型生成，它是轻量的导入/Viewer 环境。

另一台 Windows 电脑首次使用原生后端时，先准备其 Kimodo 环境，再复制 `config/pipeline.example.toml` 为根目录的 `pipeline.local.toml`，填写实际位置。模板默认后端和消费项目与工具目录同级；dotnet 使用 `$env:KIMODO_DOTNET = (Get-Command dotnet.exe).Source`，也可在 local 文件中填写实际 SDK 路径。此入口读取配置，不需要在教程中写入个人目录。

## 6. 想改 prompt，到哪里改

先确定本次 `--scope` 实际加载哪个 rules 文件；指定 `--rules` 会覆盖默认选择。

| 动作 | 主要位置 | 字段/注意事项 |
|---|---|---|
| Run | `tools/kimodo_pipeline/run_rules.json` | `locomotionOverrides.<语义名>.prompt` |
| 蹲走 | `tools/kimodo_pipeline/crouch_rules.json` | 同上，例如 `Crouch_Walk_Forward` |
| Walk、侧向及默认非道具 | `tools/kimodo_pipeline/directional_gait_rules.json`，继承 `non_prop_rules.json` | `locomotionOverrides`；部分配方的 `gaitClosure.*.prompt` |
| 普通生成节点 | `tools/kimodo_pipeline/graph.py` 的 `generate()` | 显式配方 prompt 优先，其次 `motionPromptOverrides`，最后合同 `promptDraft` |
| Mantle | `graph.py` 的 Mantle 分支 | 当前专用文案由代码构造，不能只改通用 JSON 覆盖项 |
| Air | `tools/kimodo_pipeline/air.py` 的生成节点 | 当前专用文案由代码构造；`air_rules.json` 还控制约束/周期参数 |
| StandToCrouch 等固定分支 | `graph.py` 对应分支 | 部分文案在代码内显式指定 |

**推荐复制一份同目录 rules 做实验。** 原始参考合同有哈希依赖，日常改文案不要重新格式化 `assets/config` 或批量改合同。

**WSL Bash**：

```bash
cp tools/kimodo_pipeline/run_rules.json tools/kimodo_pipeline/run_my_prompt_rules.json
```

打开副本，修改例如 `Run_Forward.prompt`，保留 direction、heading、约束和继承关系。副本放同目录，`extends` 的相对路径仍有效。先检查真正落到候选节点的文案：

```bash
python tools/produce_als_resources.py plan --scope run \
  --rules tools/kimodo_pipeline/run_my_prompt_rules.json \
  --output workspace/plans/run_my_prompt
python -c "import json; g=json.load(open('workspace/plans/run_my_prompt/graph.json')); [print(k, n['params']['prompt']) for k,n in g['nodes'].items() if n['op']=='generate']"
```

再用同一个副本生产：

```bash
python tools/produce_als_resources.py run --scope run --keep-going \
  --rules tools/kimodo_pipeline/run_my_prompt_rules.json
```

修改 `motionPromptOverrides` 不保证覆盖专用配方，最终以 `graph.json` 的 `params.prompt` 为准。新 prompt 改变生成节点身份，旧回执不能当作新文案的效果证据。

文案建议：以 `A person...` 开头，尽早写出具体动作，用适中细节，每段描述自身完整的一两个行为。精确方向/速度/支撑时序由对应约束控制，不能只堆叠形容词。比较文案时先保持模型、seed、时长、steps、CFG 和约束一致，使用新输出目录。见 [NVIDIA prompt 最佳实践](https://research.nvidia.com/labs/sil/projects/kimodo/docs/key_concepts/limitations.html)。

## 7. 每次生产后，启动 Motion Viewer 检查

生成成功、门禁拒绝或只完成部分分支，都可以检查本批已有制品。

**PowerShell**，另开一个终端并让它保持运行：

```powershell
cd $PipelineRoot
& .venv-win\Scripts\python.exe tools\start_motion_viewer.py --port 10016
```

打开 [http://127.0.0.1:10016/](http://127.0.0.1:10016/)。如果从 **WSL Bash** 启动：

```bash
source ~/Github/kimodo/.venv/bin/activate
cd "$KIMODO_PIPELINE_ROOT"
python tools/start_motion_viewer.py --config pipeline.wsl.local.toml --port 10016
```

同样用 Windows 浏览器打开这个地址。Ctrl+C 停止服务；关闭终端会停止网页。端口已占用时用 `--port 10017` 并打开对应地址，不要结束不认识的进程。10016 用来与旧工程常用的 10015 区分。

生产期间 Viewer 已在运行时，不必重启。批次登记更新后刷新网页，选择最新批次。排查网页空白时，在浏览器打开 [阶段 API](http://127.0.0.1:10016/api/stages)；应返回 JSON。不要双击 `index.html` 使用 `file://`。

### 固定检查顺序

1. **选对批次。** 查看批次 ID、来源路径和哈希，确认是本次输出。`当前项目中的 FBX` 是消费项目当前默认选择，可能与本次候选不同。
2. **生成候选 → 周期/母动作。** 看动作语义、朝向、手臂、支撑脚和周期接缝。
3. **目标重定向 raw。** 看目标骨架比例、肩臂基准、骨长以及恒定姿态偏移。
4. **Root 分解 → ALS 原地 raw。** 在共同原点看 Root 轨迹、Pelvis 残余和第一帧是否已有水平偏移；原地处理应保留身体起伏。
5. **最终 FBX。** 确认与 raw 的时间轴/朝向一致；回读通过后仍应实际播放观察。
6. **A/B 与循环。** 比原版或前一个独立批次，检查接缝、脚底支撑、滑步、手掌接触和异常穿透。
7. **回到质量与游戏报告。** 缺失阶段应显示未产出；不要从历史同名文件补齐。Viewer 骨架播放不能代替 Godot 最终蒙皮、物理和实际场景验收。

同批 generated/master/retarget/root/runtime/fbx 由生产回执自动登记。要手动登记一个既有独立制作包，可在对应配置下运行：

```bash
python -m tools.kimodo_pipeline.viewer_pack \
  --pack workspace/als/assets/generated/YOUR_PRODUCTION_VERSION/resource-pack.json \
  --label "待检查候选" --make-latest
```

## 8. CPU 方案地址与当前接入边界

以下地址在 2026-10-11 已核查：

| 方案 | 地址 | 当前意义 |
|---|---|---|
| 官方文本编码放 CPU | [Kimodo Quick Start](https://github.com/nv-tlabs/kimodo/blob/main/docs/source/getting_started/quick_start.md) | `TEXT_ENCODER_DEVICE=cpu`；扩散仍可用 GPU，适合显存较小的电脑 |
| PyTorch CPU 安装 | [PyTorch 官方安装选择器](https://pytorch.org/get-started/locally/) | 可安装 CPU 构建；本 Pipeline 的 `reuseModel` 路径支持规则 `inferenceDevice: "cpu"`，实际速度和质量需本机验证 |
| 社区 C++/GGML CPU/Vulkan | [localai-org/kimodo.cpp](https://github.com/localai-org/kimodo.cpp) | 独立 CPU 推理路线，当前不作为本 Pipeline 的可替换后端 |
| 社区原生权重入口 | [kimodo.cpp 权重说明](https://github.com/localai-org/kimodo.cpp#weights) | 依该项目 README 下载匹配模型和文本编码权重 |

若试官方 Python 的全 CPU 路线，使用单独环境/规则副本，按官方选择器安装 CPU Torch；规则启用 `reuseModel: true`、`inferenceDevice: "cpu"`，同时设置 `TEXT_ENCODER_DEVICE=cpu`。这条代码路径存在，但本次迁移没有跑全 CPU 的真实扩散生产，不提供速度承诺。

`kimodo.cpp` 当前原生 SOMA 输出为模型预测的 30 关节，README 明确列出通用约束输入与 77 关节展开尚未实现。本 Pipeline 使用 SOMA77 和精确运动学约束，所以它目前适合另行探索，不能把其 GLB 或 30 关节流直接当作这里的合格 `motion.npz`。本次也没有安装或验证该社区后端。

## 9. 常见问题

| 现象 | 先检查 |
|---|---|
| 401/403、GatedRepoError | Llama 授权是否通过、HF 登录账号是否一致 |
| Offline/local_files_only 找不到模型 | 第 3.1 节四个仓库是否完整下载到本次 HF_HUB_CACHE |
| CUDA unavailable / no kernel image | WSL GPU、Windows 驱动及 Torch 构建 |
| CMake/MotionCorrection 安装失败 | 构建工具、完整安装日志与官方环境说明 |
| Windows Godot 收到 `/mnt/...` 路径 | 是否使用新入口、正确 WSL local 配置和 Windows runtime_python |
| Reference directory exists | 已有快照直接 verify；更新时导出新版本 |
| Stage/Consumer version already exists | 选择新的输出/版本，不覆盖旧证据 |
| 改文案却没有改变候选 | 检查计划中实际 prompt、默认 scope/rules、显式复用的上游 |
| 网页无本批最终 FBX | 检查 source-quality、转换或回读失败，本批阶段可能未产出 |
| Viewer 看到的默认包还是旧包 | 新生产不会自动启用；候选和当前项目默认分别显示 |

## 10. Git 怎么用

源码、规则、教程和验证记录进入 Git。模型、token、机器路径、参考资产、生成包、缓存和日志由 `.gitignore` 排除。

Windows 没有 `git` 命令时先安装 [Git for Windows](https://git-scm.com/download/win)，重新打开终端并运行 `git --version`。WSL 的 Git 已在第 1 节通过 apt 安装。

在 PowerShell 查看改动：

```powershell
cd $PipelineRoot
git status --short
git diff
```

例如只提交一份改好的 prompt 规则：

```powershell
git add -- tools/kimodo_pipeline/run_my_prompt_rules.json
git diff --cached --check
git diff --cached --name-status
git commit -m "Tune run prompts"
```

远程仓库需另行配置；当前没有远程地址。`git commit` 保存本地版本，`git push` 上传远程，是两个独立动作。

没有远程服务器也可以把已提交源码交给另一台电脑。在本机 PowerShell 导出 Git bundle：

```powershell
git bundle create workspace/kimodo-pipeline.bundle main
```

把这个 bundle 文件复制到另一台电脑，在那台电脑上克隆，例如：

```powershell
git clone ./kimodo-pipeline.bundle ./Kimodo-Pipeline
```

这条命令在放有 bundle 的目标父目录执行。bundle 包含提交历史和源码；那台电脑仍需按前文单独安装 Kimodo、取得模型权限、准备原版 ALS 参考与消费项目，并创建自己的 local 配置。

源码与文档、资产与第三方依赖的许可范围分别见根目录的 [LICENSE.md](../LICENSE.md)、[ASSET_LICENSE.md](../ASSET_LICENSE.md) 和 [THIRD_PARTY_NOTICES.md](../THIRD_PARTY_NOTICES.md)，以及[独立目录许可边界](architecture/source-and-license-boundaries.md)。共享代码的 bundle 不包含原版参考资产或模型的使用授权。
